# ADR 0046 — UI 2.0: application shell, theme engine, white-label branding and guidance

Status: accepted (Phase 19). Builds on 0024 (reusable core), 0039 (platform experience: branding, onboarding, documents), 0042 (entitlements, navigation registry), 0044/0045 (data scope, cross-module access).

## Context

The product had grown module by module: CRM had a nested sidebar plus a tab strip, seven other layouts each carried their own hand-written tab array, dark-mode tokens existed but nothing switched them, the tenant brand could recolour only `--primary`, three different badge implementations coloured statuses independently, there was no shared tooltip/help vocabulary, and charts were a single hand-built SVG. The goal of Phase 19 is one coherent product — without touching authentication, RLS, tenancy, entitlements, permissions, data scope or object storage.

## Decisions

1. **Semantic tokens, one source.** `packages/ui/src/styles.css` gains a semantic layer (`surface*`, `border-subtle`, `text-subtle`, `primary-hover/active/soft`, `*-soft` status tints, `sidebar-*`, `focus`, `chart-1..6`) mapped in the Tailwind preset. Existing shadcn-style names (`card`, `muted`, `destructive`…) stay valid so nothing had to be mass-renamed. Components consume tokens only; raw palette colours are treated as defects. Warning/danger were darkened so status text reaches AA on its soft tint.
2. **Appearance is a user preference, not a tenant setting.** Light / Dark / System, persisted in `localStorage` (`aivoryx.appearance`), applied by a static inline `<head>` script before first paint (no flash; verified with the app bundles blocked), then kept in sync by `ThemeProvider` (OS changes, other tabs). Deliberately client-side: no table, no API. Cross-device sync is deferred.
3. **One theme engine, shared by server and client.** `@aivoryx/shared/theme` holds the colour maths, six presets (Aivoryx Teal, Ocean, Indigo, Emerald, Royal, Warm) and `deriveTheme()`. Given Primary/Secondary/Accent it derives hover/active/soft/focus and the dark-mode counterparts, enforcing WCAG AA (4.5:1) for text on the fill in both modes, and reports a problem + suggested colour when a colour is too pale. The API runs the same function to reject a bad custom theme (`BRANDING_COLOR_LOW_CONTRAST`, 422, with a suggestion); the branding UI runs it live. `buildThemeCss()` emits **brand tokens only** (`--primary*`, `--ring/--focus`, `--brand-secondary/accent`, `--chart-1..3`) for `:root` and `.dark` — status colours are never derived from a tenant colour, and the output is a fixed token grammar (HSL triples), never arbitrary CSS.
4. **The existing `BrandProvider` is extended, not replaced.** It now takes `themePreset` + Primary/Secondary/Accent, injects the derived CSS for both modes, caches it (localStorage + the head script) so the brand paints before `/auth/me`, and sets the favicon. The cache is never applied on pre-auth or platform routes and is cleared on logout.
5. **Navigation: exactly two levels, one registry.** `TENANT_NAV` is Module → Section. The sidebar, the collapsed rail (icon buttons with accessible tooltips and a section flyout), the mobile _More_ sheet and every module's in-page section strip (`ModuleShell` / `ModuleSectionTabs`, shown below `md` only) render from it — replacing eight hand-written tab arrays. A module appears when the tenant is entitled and the user holds **any** of its sections' permissions (a member limited to "My HR" still finds HR); it links to the first section the caller can open. The Field Agent PWA stays a single entry with its own chrome (ADR 0033). The mobile header/bottom-nav/More pattern is unchanged, only re-skinned. Filters and statuses are never navigation.
6. **Option C adaptive sidebar.** Light neutral in light mode, navy in dark; active = subtle tint + accent text + a 2px indicator (no saturated pill). Collapsed state persists per browser.
7. **Capability-driven workspace, no role names.** The dashboard registry already composed widgets from `module` + `permissions`; Phase 19 adds a self-service "My day" widget (`hr.attendance.self`), a lead-trend chart widget, and orders sections Identity → Key metrics → Primary work → Analysis. Nothing branches on a role name or tenant vertical.
8. **Guidance is one small vocabulary.** `Tooltip` (packages/ui; portal-positioned, hover + focus + Esc, `aria-describedby`), `HelperText`, `InfoPopover`, `ContextualHelp` (driven by a shared glossary), `ModuleWelcome` (first-use card for one module, dismissible), `FeatureTourHost` (3–5 step tours, skippable, re-runnable from Help), `HelpCenter`, and a richer `EmptyState`. Completion/dismissal state is per browser (`localStorage`) — guidance may reappear on a new device, which is harmless — so no schema was added for it.
9. **Documentation is external and configurable.** Help topics carry stable paths (`crm/leads/managing-leads`); `NEXT_PUBLIC_HELP_BASE_URL` / `NEXT_PUBLIC_SUPPORT_EMAIL` decide whether links exist. Unset → the Help Center still works from in-app summaries and simply omits links. No domain is assumed.
10. **Charts have a capability model.** A dataset declares a shape (time series / categorical / target) and only the valid kinds are offered (time series: line, area, column; categorical: bar, column, donut, pie; target: gauge, progress, bar). `InteractiveChart` adds date range, expand-to-large with summary metrics, "open in new tab", CSV export of the data on screen (formula-neutralised), and a remembered kind. A report registry (`/reports/[id]`) renders the _same_ definition standalone; access is checked client-side only to decide whether to offer it — the data endpoints stay the authority. Hand-built SVG, no new dependency.
11. **One badge primitive.** `Badge` + semantic tones; `StatusBadge` / `SupplyStatusBadge` / `HrStatusBadge` delegate to it. Each module keeps its own status→tone map (the same word means different things per domain).
12. **Document branding is a reusable capability of the existing engine**, not a quotation feature: `DocumentBrandingContext` (already used by quotations, invoices, receipts, credit notes) gains the effective document logo (`company` vs `separate`, own asset kind `logo_document`), a print-safe accent (`documentAccent`, ≥4.5:1 on white, independent of the app theme), and `showCustomerLogo`. A customer logo (`customers.logo_*`, optional upload) is read **only** when the tenant enabled the flag and the document carries `party.customerId`; off by default, never read otherwise.
13. **Tenant-aware sign-in (config-driven, not type-driven).** `/login?workspace=<slug>` resolves branding through a `@Public()` endpoint that returns a minimal, safe field set (or a generic 404 for unknown / inactive / malformed slugs) and streams only the login logo (falling back to the primary logo). Slug → tenant resolution uses a new SELECT-only RLS policy bound to an `app.workspace_slug` GUC (the same pattern as invitation tokens); everything else is read through the normal tenant-scoped policies. Unknown workspace → neutral, industry-agnostic Aivoryx branding. Authentication itself is untouched: one login, one session model; branding is presentation.

## Data model

Migration `0023`: `tenant_asset_kind` += `logo_compact`, `logo_login`, `logo_document`; `tenant_company_profiles` += `theme_preset`, `secondary_color`, `document_accent_color`, `document_logo_mode`, `document_show_customer_logo`; `customers` += `logo_object_key`, `logo_content_type`, `logo_updated_at`. Migration `0024`: `tenant_company_profiles` += `login_welcome`, `login_description`, `login_show_powered_by`; `tenants_by_public_slug` policy. Existing tables/RLS/audit conventions are reused; bytes stay in the provider-neutral `ObjectStorageService` and are served through authenticated routes (tenant assets) or the deliberately public login-logo route.

## Consequences

- Existing workspaces keep working: no preset stored + a legacy `primary_color` = a "custom" theme; document behaviour defaults to today's (company logo, footer, no customer logo).
- A tenant's brand can never change status semantics, security, permissions or authentication behaviour.
- Module pages no longer carry navigation arrays; adding a section is a registry entry.
- Deliberate limits: appearance and guidance state are per browser; the login logo needs the workspace URL (custom domains / subdomain resolution are deferred); charts are limited to the datasets that have permissioned endpoints today.

## Deferred

Cross-device appearance/guidance sync, per-user dashboard layout/customisation, subdomain/custom-domain workspace resolution, a Field Agent app inside the desktop shell, additional reports (finance, supply) once dataset endpoints exist, per-document-type branding overrides.
