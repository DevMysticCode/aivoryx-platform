# ADR 0048 — Inbound webhook hardening and raw-event retention

Status: accepted (Universal Connector UC-1). Builds on 0032 (inbound integration engine and connector security), 0037 (notification worker, in-process poll pattern) and the UC-0 characterization suite (`apps/api/test/integrations-contract.int.spec.ts`).

## Context

The Pabbly connector (0032) is verified against a real workflow, but the public webhook had operational gaps: no explicit body-size limit, no rate limiting, a raw event left `RECEIVED` forever, an unexpected exception that could leave an event invisible or ambiguous, no retention of raw customer payloads, and an admin page whose sidebar permission (`memberships.read`) differed from the API's (`crm.integrations.manage`).

UC-1 fixes these without introducing the adapter/engine architecture (UC-2+). The route, credentials, tables and response semantics are unchanged.

## Decisions

1. **Body limit is scoped to the public webhook and enforced by the parser.** `configureApp` mounts a `body-parser` JSON/urlencoded pair on `/api/v1/integrations/webhooks` _before_ the framework defaults, limited by `WEBHOOK_MAX_BODY_BYTES` (default 256 KiB, 1 KiB–5 MiB). An oversized request is rejected from `Content-Length` / while streaming with `413 PAYLOAD_TOO_LARGE`, before authentication, the controller, the database or any queue. Other routes keep the framework default (100 KiB). We depend on `body-parser@1.20.3`, the exact version Nest's own parser uses, because 1.x marks `req._body` so the second (default) parser skips an already-parsed request; `body-parser` 2.x (Express 5's `json`) does not, which double-parses and fails ("stream is not readable"). Client (4xx, `expose`) errors from Express middleware now keep their status in the global exception filter instead of becoming a 500 (this also fixes the default limit, which previously surfaced as 500).
2. **Rate limiting is per authenticated source, in-process, behind an interface.** `RateLimiter` (`consume(key)`) is injected via `WEBHOOK_RATE_LIMITER`; the initial `TokenBucketRateLimiter` is in memory with an injectable clock. The key is `source:<sourceId>`, consumed _after_ the connector secret is proven and _before_ anything is persisted, so a limited request creates no raw event, canonical event, lead or outbox row. Response: `429 RATE_LIMITED` with `Retry-After` and `details.retryAfterSeconds`. Defaults: burst `WEBHOOK_RATE_LIMIT_MAX=120`, refill over `WEBHOOK_RATE_LIMIT_WINDOW_SECONDS=60` (sustained 2 events/s per source — a bulk push of 100+ leads fits, a runaway loop is stopped). **Deliberately not scoped by URL source key** (public, guessable: strangers could drain a real source's bucket) **or by client IP** (the API has no trusted-proxy configuration; behind Render/Vercel `req.ip` is the proxy's shared address, so an IP bucket would let one caller throttle everyone; forwarded headers are not trusted). Wrong-secret traffic never touches a real source's bucket. Because it is per process, N API instances allow up to N× the limit; a Redis implementation can replace the provider later without changing connector code.
3. **Raw-event lifecycle uses the existing enum.** `DONE` → `PROCESSED`; a validation/mapping failure → `FAILED` (replayable); a duplicate logical event's own delivery → `PROCESSED`; an exact redelivery (`DUPLICATE_RAW`) leaves the original untouched; replay ends in `PROCESSED` or `FAILED` by outcome.
4. **Unexpected failures are recorded, never left ambiguous.** The two-transaction design is kept. If transaction 2 throws, it rolls back (no half-written lead), then a separate short transaction marks the raw event `FAILED` and the canonical event `FAILED` with `PROCESSING_ERROR` (inserting it if the first attempt never persisted one; updating the `PROCESSING` row a replay left), plus a stage-log entry carrying the raw event's correlation id. The caller gets a generic `500` (the original error can embed SQL parameters, i.e. lead data, so it is neither propagated nor logged — only the error class and SQLSTATE are). A provider **retry of the same delivery** whose event is `FAILED/PROCESSING_ERROR` is reprocessed through the replay path (one lead, attempt counted); business failures are not retried automatically because the same body would fail again. A corrected resend with a _different_ body but the same provider record id is still treated as a duplicate event (unchanged behaviour); it needs an admin replay of the original.
5. **Retention.** `raw_events.expires_at` (migration `0026`, indexed) is set at insert from `RAW_EVENT_RETENTION_DAYS` (default 30) for success and failure alike; the DB default only backstops legacy rows (legacy rows expire 30 days after the migration). Nothing is deleted on success. Secrets were never stored (hash-only credentials; `Authorization` is excluded from `transport_metadata`).
6. **Purge is bounded, in-process and DB-guarded.** `RawEventRetentionService` runs on the existing self-rescheduling poller (no new worker) every `RAW_EVENT_PURGE_INTERVAL_MINUTES` (default 60), in batches of `RAW_EVENT_PURGE_BATCH_SIZE` (default 500), at most 20 batches per run. Each batch is its own short transaction; concurrent runs cannot double-delete. It runs cross-tenant through `withRawEventPurgeContext` (`app.raw_event_purger`), which two new policies (`raw_events_purge_read/delete`, following the outbox-dispatcher precedent) restrict to rows **already past `expires_at`** — a bug cannot remove a live row. Deleting a raw event cascades (existing FKs) to its canonical event and stage log; CRM leads have no FK to them and are never touched. Consequence: after expiry the event's idempotency record is gone, so a provider re-sending a very old record id is re-processed, and lead-level dedupe (phone/email) collapses it into the existing lead. No `FOR UPDATE` is used (it would need an UPDATE policy).
7. **One capability.** The Integrations sidebar entry and the page gate use `crm.integrations.manage`, the permission every `admin/integrations` route enforces. `memberships.read` no longer reveals or grants connector management. The API remains the authority.
8. **Observability.** One structured, secret-free line per delivery (`webhook.ingest`: correlationId, tenantId, sourceId, rawEventId, canonicalEventId, status, errorCode, durationMs); rejected deliveries log status `REJECTED` with the error code. No payload, header or credential is logged; pino already removes `Authorization`.

## Consequences

- The Pabbly route, credentials, response shapes and idempotency behaviour are unchanged (UC-0 suite green). The only intentional behavioural changes: `raw_events.status` now advances, oversized bodies get `413 PAYLOAD_TOO_LARGE`, an abusive source gets `429`, and unexpected failures are durable and retry-safe.
- Migration `0026` is additive (a column with a stable default, one index, two policies).
- Deferred: IP-scoped and distributed rate limiting (needs trusted-proxy config / Redis), automatic retry with backoff and dead-lettering, a durable `duration_ms` column, admin UI for event detail and mapping (UC-5), a corrected-body resend after a failure.
