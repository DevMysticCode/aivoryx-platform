### 1d. HR incentive/expense double-counting across overlapping payroll periods — confirmed, now fixed (see §1f)

**No code change in the session that wrote this section** — it documents the reproduced defect only. The fix is implemented and verified in §1f below; this section is kept as the historical record of the original bug.

The §1c observation above is now confirmed with persisted-state evidence, and the gap is wider than first described: incentives have a _racy, partial_ consumption marker; expenses have _none at all_.

**Policy options (not chosen — this is the unresolved decision for a product owner):**

1. **Single consumption, enforced at creation**: reject creating a payroll period whose date window overlaps any existing non-cancelled period for the tenant (mirrors the `leave`/`attendance` exclusion-constraint convention already used elsewhere in this exact module). Simplest, matches existing codebase idioms, but forecloses any legitimate reason to run overlapping periods (e.g., a supplementary/off-cycle run alongside a regular monthly one).
2. **Single consumption, enforced at the item**: give `hr_expense_reimbursements` the same `payrollPeriodId` consumption marker `hr_incentives` already has (nullable FK, set at `finalize()` time, filtered by `IS NULL` at `process()` time), and additionally make incentive consumption a true reservation at `process()` time (not just at `finalize()`) so two periods can't both draft the same item in the first place — would still require deciding what happens to a DRAFT period's stale snapshot if the item gets consumed by a different period before this one finalizes (reject at finalize? silently exclude and recompute?).
3. **Explicit installment/recurring allocation**: if overlapping periods are intentionally supported (e.g., a correction run), each incentive/expense would need its own remaining-balance or allocation-quantity tracking rather than a single consumed/unconsumed flag — a materially larger change.

**Recommendation for product-owner approval**: Option 2 is the smallest change consistent with the one consumption marker that already exists (incentives) and extends the identical pattern to expenses, without foreclosing any currently-supported workflow. Option 1 is simpler to implement but is a product-level restriction (no overlapping periods, ever) that hasn't been asked for and could block a legitimate off-cycle run. Not implementing either without this decision.

### 1e. Payroll item consumption — implementation-ready design (now built — see §1f)

**This section is the design that was approved and implemented. No further changes to it this session; see §1f for the build.**

#### Current lifecycle, traced exactly

| Entity                                                                                                                                      | States                                                                                                                               | How it moves                                                                                                                                                                                                                                                                                                  | Who/what can undo it                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Incentive** (`hr_incentives`)                                                                                                             | `DRAFT → APPROVED → REJECTED`\*, and `APPROVED → PAID` (set only as a side effect of a payroll `finalize()`, never its own endpoint) | `create()` (DRAFT) → `approve()` (APPROVED). No reject endpoint exists despite the status enum allowing it — `IncentivesService` only exposes `create`/`approve`/`list`/`get`.                                                                                                                                | Nothing — there is no un-approve, no delete                                                                                                                                                         |
| **Expense claim** (`hr_expense_claims`) + **reimbursement** (`hr_expense_reimbursements`, 1:1 via a unique `(tenant_id, expense_claim_id)`) | `DRAFT → SUBMITTED → APPROVED → REIMBURSED`, with `cancel()` from most pre-reimbursement states                                      | `createClaim` → `submit` → `decide` (approve/reject) → `reimburse` (creates the 1:1 reimbursement row, status `PAID`/`FAILED`)                                                                                                                                                                                | `cancel()` exists for the claim pre-reimbursement; nothing reverses a reimbursement once recorded                                                                                                   |
| **Payroll period** (`hr_payroll_periods`)                                                                                                   | `DRAFT → PROCESSING → FINALIZED → PAYMENT_PROCESSING → PARTIALLY_PAID → PAID`                                                        | `create` (DRAFT) → `process` (rebuilds every entry from scratch each call — "clear any prior draft entries" then re-insert) → `finalize` (freezes each entry's `snapshot` JSONB, marks unconsumed incentives for this run's employees as consumed) → `recordPayment` (one or more partial payments per entry) | **No cancel, reopen, or delete exists for a period at any status.** `process()` is the only "undo" — it deletes and rebuilds that period's own draft entries, but has no effect on any other period |
| **Payroll entry** (`hr_payroll_entries`)                                                                                                    | `PENDING → PARTIALLY_PAID → PAID / FAILED` (payment status; separate from the period's own status)                                   | Rebuilt wholesale by every `process()` call on its period; `snapshot` frozen once at `finalize()` and never touched again — by design, "changing the employee's salary, department, leave or expenses afterwards never alters" a finalized entry                                                              | None — immutability is intentional (confirmed by an existing test)                                                                                                                                  |

\* `REJECTED` is a modeled status with no code path that reaches it.

**The asymmetry that causes the bug**: the incentive query's own comment claims "dated in window" but the actual `WHERE` has no date predicate at all — incentive eligibility is purely consumption-state (`status = 'APPROVED' AND payroll_period_id IS NULL`), making it _order-sensitive_ across periods but not _window-sensitive_. The expense query is the opposite: purely window-sensitive (`payment_date BETWEEN period_start AND period_end`), with no consumption-state column to even check. Neither one is "wrong" in isolation; the combination of a non-reserving consumption check (incentives) and a non-existent one (expenses), with no constraint stopping overlapping periods from being created in the first place, is what produces the double payment.

**Payment recording and external integration**: `recordPayment` is HR's own bookkeeping only ("Operational payment state only — Aivoryx is not a bank," per the schema's own comment) — multiple partial-payment rows per entry are intentional and already supported; there is no external payment-gateway integration to consider for this design.

#### Policy comparison

|                                                                              | Prevents the bug                                                                                                                                                                                                                      | Blocks any current workflow                                                                                                                                                                                                                                                                                                              | Matches an existing codebase convention                                                                            | Change size                                                                                                                                      |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. Forbid overlapping periods** (DB exclusion/check at `create()`)         | Yes, by construction — no overlapping period can ever exist                                                                                                                                                                           | **Yes, speculatively**: nothing in the repo exercises or documents a legitimate off-cycle/correction/supplementary run, but nothing rules one out either. A true off-cycle run (e.g., a one-time bonus payout mid-month) would need its _own_ period today, and would be blocked by this if its dates overlap the regular monthly period | Yes — identical in spirit to `leave`'s exclusion constraint and `attendance`'s same-day guard                      | Smallest: one migration, one `create()` check                                                                                                    |
| **2. Reserve each item for one period** (extend the existing marker pattern) | Yes, if reservation happens at `process()` time, not just `finalize()` time (the current gap)                                                                                                                                         | No currently-exercised workflow requires overlapping periods to share an item — reservation only stops _literal_ double-use, not overlapping periods existing for unrelated employees/items                                                                                                                                              | Yes — extends the exact mechanism `hr_incentives.payroll_period_id` already uses, onto `hr_expense_reimbursements` | Small–medium: one migration (new column + constraint), service changes to both `process()` and `finalize()`, a release path for abandoned drafts |
| **3. Explicit installment/allocation tracking**                              | Only if the business actually wants partial/split consumption (e.g., a bonus paid half this period, half next) — single-consumption bugs would need to be a _special case_ of the general allocation logic, not solved by it directly | No — this is additive, not restrictive                                                                                                                                                                                                                                                                                                   | No existing precedent in this codebase for allocation/remaining-balance tracking on a financial item               | Largest: a new allocation table, remaining-amount tracking, UI for partial allocation, materially more test surface                              |

**The repository does not establish which of these is wanted.** Nothing in the product today exercises split/installment payments, off-cycle runs, or payroll correction workflows — but nothing documents that it has deliberately decided not to support them either. Recommending option 2 is therefore a recommendation of the _smallest, least-restrictive, convention-consistent_ path, not a claim that the business has ruled out options 1 or 3.

**Recommendation (unchanged from §1d, now with the workflow-impact analysis Phase 2 asked for): Option 2.** It fixes exactly the confirmed bug, extends a pattern the codebase already trusts (`hr_incentives.payroll_period_id`), and — unlike Option 1 — does not need to take a position on whether overlapping periods are legitimate, since it makes overlapping periods safe rather than forbidding them.

#### Proposed reservation state model (Option 2)

Per-item states, expressed without adding a new status _column_ where the existing one already carries the needed meaning:

| State                                      | Incentive representation                                                                                                       | Expense reimbursement representation (new)                                                                                                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Available**                              | `status = 'APPROVED'`, `payroll_period_id IS NULL`                                                                             | `status = 'PAID'` (reimbursement already made), new `payroll_period_id IS NULL`                                                                                                                             |
| **Reserved by a draft**                    | `payroll_period_id = <period>`, incentive `status` unchanged (`APPROVED`)                                                      | `payroll_period_id = <period>`                                                                                                                                                                              |
| **Consumed (finalized)**                   | `payroll_period_id = <period>`, `status = 'PAID'`                                                                              | `payroll_period_id = <period>` (no separate "paid" concept needed — a reimbursement is already the terminal expense-payment event; the payroll period's own status governs whether _that run_ is finalized) |
| **Released** (draft abandoned/reprocessed) | `payroll_period_id` set back to `NULL`; `status` stays `APPROVED` (never touched by reservation/release, only by `finalize()`) | `payroll_period_id` set back to `NULL`                                                                                                                                                                      |

No new state value is needed on either table — "Reserved" and "Consumed" are distinguished by the _owning period's own status_ (`PROCESSING` vs `FINALIZED`), not by a new column on the item. This avoids two sources of truth staying in sync. A genuinely new column is needed only on `hr_expense_reimbursements` (it has none today); `hr_incentives` already has `payroll_period_id` and only needs behavioral changes (reserve earlier, release on reprocess).

**Why not a dedicated allocation/reservation table instead of extending the nullable FK**: a dedicated table (`hr_payroll_item_reservations(tenant_id, item_type, item_id, payroll_period_id, reserved_at)`) would be the more "general" design and is the natural fit _if_ Option 3 (partial/installment allocation) is ever approved, since it alone can express "this item is 40% allocated to period A, 60% to period B." For single consumption (Option 2) it is strictly more machinery than needed: it adds a join on every `process()`/`finalize()` call, a second place the invariant can drift from the item's own row, and a new table to RLS-scope and audit, for no behavior the extended-FK approach can't already express. **Recommendation: extend the nullable FK, not a new table** — revisit a dedicated table only if/when Option 3 is separately approved.

#### Transaction and concurrency strategy

- **Atomic, tenant-scoped reservation**: reservation happens inside `process()`'s existing `withTenantContext` transaction. The _selection_ query for both incentives and expense reimbursements becomes `SELECT ... WHERE payroll_period_id IS NULL ... FOR UPDATE`, exactly mirroring the row-locking pattern already used by `payroll.service.ts`'s own `lock()` (on the period) and `recordPayment`'s entry lock, and by `allocations.service.ts`/`inventory-core.ts` elsewhere in this codebase — immediately followed, in the same statement group, by `UPDATE ... SET payroll_period_id = <this period> WHERE id = ANY(<locked ids>) AND payroll_period_id IS NULL`. The `AND payroll_period_id IS NULL` on the `UPDATE` (not just the preceding `SELECT`) is the actual safety net: even if two transactions' `FOR UPDATE` selects somehow returned overlapping sets (they can't, under row-level locking, but this is a correctness belt-and-suspenders matching the "atomic conditional update" idiom already used for Field visits and CRM leads in earlier milestones), only one `UPDATE` can ever flip a given row from `NULL` to non-`NULL`.
- **Concurrent attempts from different periods**: with the `FOR UPDATE` lock on the candidate item rows, a second period's `process()` attempting to reserve the _same_ item blocks until the first commits (or rolls back), then re-reads under its own fresh statement snapshot and correctly sees the row already reserved — it is simply excluded from the second period's draft, not an error. This is the same serialization shape as the tenant-admin and Field/CRM fixes from earlier milestones, but importantly _lock-ordering-safe_ here: each item is only ever locked by whichever single period's `process()` call is currently trying to claim it, never by two periods trying to lock each other's distinct items in opposite order (unlike the original tenant-admin bug), so there is no analogous deadlock risk to design around.
- **Idempotent reprocessing of the same draft**: `process()` already deletes its own prior entries first. Extend this to also release (`payroll_period_id = NULL`) every item currently reserved by _this_ period before re-running selection — otherwise a second `process()` call on the same still-DRAFT period would see its own prior reservations as "already taken" and silently exclude them from the rebuilt draft.
- **Partial failure and rollback**: no change needed beyond what the existing transaction already guarantees — reservation, entry/component insertion, and the period total rollup are all one `withTenantContext` transaction already; if anything after the reservation throws, the whole transaction (including the reservation) rolls back, which is exactly "release on failure" for free.
- **Finalizing only a run's own reservations**: `finalize()` already queries `payrollEntries WHERE payrollPeriodId = id` and derives which incentives to flag from `entries.map(e => e.employeeId)` — it has no concept of "this specific reserved set," only "whatever entries this period currently has." Extend it to instead consume (flip incentive `status`, and now also flip the new expense marker) for exactly the item rows whose `payroll_period_id` already equals this period — not a fresh re-selection — so finalize can never accidentally consume an item it didn't actually reserve at process time.
- **Safe reservation release**: needed in exactly one new place — a (currently nonexistent) "abandon this draft" action, if one is ever added, would simply release every item reserved by that period and leave it `DRAFT`/empty. Until such an action exists, the only release path is reprocessing, covered above.
- **Duplicate payment recording**: already handled today — `recordPayment` locks the specific entry `FOR UPDATE`, so this design doesn't need to touch it. Worth noting for completeness, not a gap this design closes.
- **Auditability**: both `process()` and `finalize()` already write `audit.record(...)` rows; no new audit action is needed — the existing `hr.payroll.processed`/`hr.payroll.finalized` metadata can simply note the count of incentive/reimbursement items reserved or consumed, mirroring the `employeeCount`/`netTotal` fields already recorded.
- **Migration and legacy data**: the new `hr_expense_reimbursements.payroll_period_id` column is additive and nullable — every existing reimbursement row defaults to `NULL` ("available"), which is the correct interpretation for data that predates this change (nothing retroactively marks a past reimbursement as already paid out through payroll, since today's system never tracked that). The one real legacy-data question: **finalized periods that already exist today may have double-counted an item under the current bug.** This design does not and cannot retroactively detect or correct that — a one-time data audit (comparing `hr_payroll_entry_components` rows with `source = 'reimbursement'` or `'incentive'` against overlapping periods' date windows) would be a separate, explicit data-remediation task, not part of this schema change, and is called out here as a decision the product owner needs to make a call on (ignore historical double-pay, or run a manual reconciliation).

#### What this design does **not** decide

- Whether overlapping payroll periods should remain unrestricted (Option 2 makes them _safe_, not _intentional_ — the product owner may still separately want Option 1's creation-time guard as a UX improvement, independent of this fix).
- Whether a `REJECTED` incentive status needs its own endpoint (out of scope — unrelated to consumption).
- Whether a period "abandon/cancel" action should be added — this design's release mechanism (reprocessing) covers today's only real-world path to abandoning a draft; a dedicated cancel endpoint is a separate product decision.

### 1f. Implemented: atomic HR payroll item reservations (Option 2, approved scope)

**Built and verified this session.** Overlapping payroll periods remain allowed, by design; no cancellation workflow or installment/allocation support was added, matching the approved scope exactly.

**Schema** — `packages/db/drizzle/0030_zippy_kingpin.sql` (additive, nullable, no FK — mirrors `hr_incentives.payroll_period_id`'s own precedent exactly, for the same reason: the application is the sole writer and periods are never deleted):

```sql
CREATE INDEX "hr_expense_reimbursements_payroll_period_idx" ON "hr_expense_reimbursements" USING btree ("tenant_id","payroll_period_id");
```

**Reservation and finalization transaction behavior** — `apps/api/src/hr/payroll.service.ts`:

- `process()` now, inside its existing single `withTenantContext` transaction: (1) releases this period's own prior reservations (`payroll_period_id = NULL` for rows where it currently equals `id`) before rebuilding, making a rejected reprocess attempt harmless and a hypothetical future "revert to draft" path safe; (2) per employee, claims incentives via `UPDATE hr_incentives SET payroll_period_id = <this period> WHERE ... AND payroll_period_id IS NULL RETURNING *` — a single atomic conditional update, not a separate lock-then-write step, so two periods' `process()` calls racing on the same row simply can't both match it (whichever commits first wins; the other's `WHERE` clause excludes the now-claimed row once it's visible); (3) claims expense reimbursements the same way, via a claim-id lookup (plain read — claim status doesn't change here) followed by the same atomic conditional `UPDATE` on `hr_expense_reimbursements`.
- `finalize()` now consumes (`status = 'PAID'`) only incentives whose `payroll_period_id` already equals _this_ period — a fresh re-selection by employee/date was removed entirely. Expense reimbursements need no equivalent step: their `payroll_period_id` was already set at `process()` time and nothing else can release it.
- No lock-ordering design was needed: each claim is a single UPDATE statement (not a separate SELECT…FOR UPDATE followed by a later write), so there is no multi-step lock-acquisition sequence for two periods to deadlock over — unlike the earlier tenant-admin fix, this invariant has no analogous risk to guard against.
- Transaction atomicity is unchanged from before this fix: reservation, entry/component rebuild, and the period total rollup were already one transaction; a failure anywhere after a reservation rolls the reservation back for free, verified directly (see below) rather than assumed.

### 1g. Historical payroll duplicate-payment assessment — read-only investigation, no data touched

**No production data read, no rows mutated.** This investigation was conducted entirely against a local isolated test database with synthetic fixtures (`RUN_DB_IT=1`); nothing here is a claim about real tenant data, because no real tenant data was examined.

#### The central finding: historical evidence has no stable source-item identifier

Traced exactly how a finalized payroll entry retains (or doesn't retain) its source incentive/reimbursement:

- `hr_payroll_entry_components` — the row written for every incentive/reimbursement baked into an entry — has **no foreign key or id column pointing back to the `hr_incentives` or `hr_expense_reimbursements` row it came from.** Its only fields are `kind`, `source` (`'incentive'`/`'reimbursement'`), `name` (free text — the incentive's `type`, or the literal string `'Reimbursement'` for every expense, with no further detail), and `amount`.
- The frozen `snapshot` JSONB on `hr_payroll_entries` (written once at `finalize()`) copies the exact same shallow fields — `kind`/`name`/`amount`/`source` — again with no id.
- `hr_payroll_payments` records actual payment execution, but only at the **whole-entry level** (one employee's entire netted payroll for one period), never per-component — so payment evidence can confirm "this employee's payroll for this period was paid," never "specifically the incentive portion was paid," since multiple components are netted into one figure before any payment is recorded.
- For **incentives**, the `hr_incentives.payroll_period_id` column existed before this session (migration predates 0030) and is a single nullable scalar — it can only ever show the _one_ period that most recently claimed it. Under the pre-fix code, if two periods both drafted the same incentive and both finalized, the row ends up pointing at whichever period's `finalize()` ran _first_ (the second one's `UPDATE ... WHERE payroll_period_id IS NULL` simply doesn't match anymore) — so **the incentive row's current state is indistinguishable between "used once" and "used twice historically."**
- For **expense reimbursements**, there was no consumption tracking at all before migration 0030 — every pre-existing row's new `payroll_period_id` column defaults to `NULL` regardless of how many times it was actually included in a finalized period historically. The column cannot be used to infer _anything_ about pre-fix history; it only starts being meaningful for processing that happens after this fix shipped.

**Consequence**: any audit of payroll periods finalized before this session's fix can only ever produce a **heuristic match** — same employee + same `kind`/`source`/`name`/`amount` across two or more distinct finalized periods — never a certain one. This is a property of the historical data itself, not a limitation of the query that could be worked around with a cleverer join.

#### Confirmed vs. suspected: the criteria actually used

| Classification                                        | Criteria                                                                                                                                                                                                                                                     | What it does and doesn't prove                                                                                                                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Not a candidate**                                   | The (employee, kind, source, name, amount) combination appears in only one finalized-or-later period's components                                                                                                                                            | Correctly excludes ordinary, non-duplicated items — including legacy reimbursements with a `NULL` marker that were only ever used once                                                                  |
| **SUSPECTED_DUPLICATE_INCLUSION_PAYMENT_UNCONFIRMED** | The combination appears across 2+ distinct finalized-or-later periods, and at least one of the contributing entries has no `PAID` row in `hr_payroll_payments`                                                                                               | The calculation included the (heuristically) same item twice; whether money actually moved for both is not established — e.g. one period may still be unpaid                                            |
| **SUSPECTED_DUPLICATE_PAYMENT**                       | The combination appears across 2+ distinct periods, and _every_ contributing entry has at least one `PAID` payment row                                                                                                                                       | The strongest signal available: money was recorded as paid out under two separate payroll entries for what heuristically looks like the same incentive/reimbursement. Still not a certainty — see below |
| **CONFIRMED**                                         | **Not a status this diagnostic can ever produce, for any period finalized before this fix**, because no query can rule out "two different items that happen to share employee + name + amount" without a stable id that doesn't exist in the historical data | Explicitly not claimed — doing so would be inventing certainty the data doesn't support                                                                                                                 |

The diagnostic (`apps/api/test/hr-payroll-duplicate-diagnostic.int.spec.ts`) deliberately keeps "same amount, different genuinely-separate item" (its scenario C) as a **surfaced, not-silently-dropped, never-escalated-above-suspected** case — exactly the behavior the investigation's constraints require (never conclude duplication from amount/date/employee alone, but also never hide a plausible case).

#### Is a reliable read-only assessment feasible?

**Partially.** The diagnostic above is real, read-only, and validated against five synthetic scenarios (duplicate-unpaid, duplicate-paid, false-positive-same-amount, no-payment-evidence, and an untouched legacy row) plus a tenant-isolation check — all passing. It is a sound way to **surface candidates for human review**. It is **not**, and cannot be made into, a way to _confirm_ historical duplicate payment, because the underlying data was never recorded with the identifier that would make confirmation possible. Running it against real tenant data (not done here — no production or staging data was read) would produce a list of _suspected_ cases, each requiring a human to look at the surrounding context (dates, documents, employee records) to judge plausibility — the diagnostic cannot do that judgment itself.

#### Recommended product-owner decision

1. **Whether to run this diagnostic against real tenant data at all.** If the system has not yet processed real payroll (consistent with this being a pre-launch readiness engagement), the question may be moot — confirm with the product owner whether any tenant has actually run payroll before this fix shipped.
2. **If real historical payroll exists**: run the same read-only query (reproduced in this section) against that environment under explicit authorization, and route every `SUSPECTED_*` finding to a human for manual judgment — not automated correction. No automatic remediation should ever run against a `SUSPECTED` classification, given the diagnostic's own acknowledged inability to confirm.
3. **What additional data would improve future confirmability** (not retroactively, but going forward): none needed — this session's fix (`payroll_period_id` on both tables, claimed atomically at `process()` time) already prevents new duplicate inclusion by construction. The gap in confirmability is permanent for anything finalized _before_ the fix and cannot be closed after the fact without inventing a provenance link the original data never recorded.

## 15. Lead Ingestion Failure Recovery and Replay Safety

Uses the §13 taxonomy (PASS/FAIL/PARTIAL/BLOCKED/NOT TESTED).

### 15.0 The actual ingestion lifecycle — corrected architecture fact

**There is no BullMQ-backed queue or worker for lead ingestion.** Receipt,
raw-event persistence, canonicalization, dedup and lead creation all run
_synchronously inside the inbound HTTP request_, across exactly two
database transactions (`ingestion.service.ts`'s own doc comment: "Two
transactions, not one — the raw event must survive even if everything after
it fails"). BullMQ exists in this codebase only for **notification
delivery** (`NotificationsWorker`), a decoupled, downstream concern — losing
a notification about a created lead is not the same as losing the lead
itself. Every item in this milestone's scenario list framed around "a
worker fails after receiving a job" / "a queue job delivered more than
once" therefore maps onto a different real mechanism here: the request
process dying between the two transactions, or during a replay attempt —
which this milestone reproduced directly (§15.2), not by assuming a queue
that does not exist.

**Correction to this document's own earlier §13.1/§13.9 finding**: "no
dead-letter state" is not quite accurate. `canonical_lead_events.status`
already includes `DEAD_LETTER` and `NEEDS_REVIEW` as reserved enum values,
exactly as ADR 0032 and `docs/architecture/RAW-EVENTS-AND-REPLAY.md`
describe — the schema-level feature exists. What does not exist is the
code path that would ever _set_ either value: ADR 0032's model expects a
BullMQ-backed retry loop with "exhausted retries → `DEAD_LETTER`," and that
loop was never built for ingestion (only `replay()`'s admin-triggered,
uncapped retry exists). This milestone's fix (§15.3) deliberately does not
wire up `DEAD_LETTER` either, for the reason given there — but the
corrected framing matters for anyone reading the schema cold.

Confirmed real states/transitions (unchanged from §13.1, re-verified):
`raw_events.status`: `RECEIVED → PROCESSED | FAILED` (set once, at the end
of a definitively-resolved attempt). `canonical_lead_events.status`:
`RECEIVED → PROCESSING → {DONE, VALIDATION_FAILED, MAPPING_FAILED, FAILED}`,
with `FAILED` retryable only when `lastErrorCode` is `PROCESSING_ERROR` or a
retryable hydration code (`isRetryableHydrationErrorCode`).

### 15.2 Confirmed defects (reproduced against the pre-fix code, then fixed)

**Defect A — a crash immediately after the raw event is persisted (or a
"double fault" where `recordProcessingFailure` itself also fails) leaves
the raw event stuck at `RECEIVED` with no canonical row, forever. A
provider redelivery of the identical payload was answered `DUPLICATE_RAW`
— treating a lead that was NEVER processed as if it had already been
handled. The lead was silently and permanently lost**, and — because
`listEvents`/`getEventDetail` are keyed off `canonical_lead_events`, not
`raw_events` — it was also invisible in the admin UI. Severity: **data
loss**, the single highest-priority category in this milestone's own
ranking.

- Reproduction: `apps/api/test/ingestion-failure-recovery.int.spec.ts`
  "a stale orphaned RECEIVED raw event with no canonical row is safely
  reprocessed on redelivery, not silently reported as a duplicate" —
  arranged via the same existing BOOM- trigger seam
  (`integrations-hardening.int.spec.ts`) plus a second trigger forcing
  `recordProcessingFailure`'s own write to also fail, exactly matching that
  method's own comment: _"double fault: the event stays RECEIVED and a
  redelivery is handled as a new attempt"_ — which this test proved was
  **not actually true** before the fix.
- Root cause: `IngestionService.run()`'s duplicate-check branch only
  treated a redelivery as retry-eligible when `rawStatus === 'FAILED'`; a
  row stuck at `RECEIVED` with no canonical event never matched that
  condition.
- Fix (`apps/api/src/integrations/ingestion.service.ts`): when no
  canonical row exists, the raw event is still `RECEIVED`, and the raw
  event's `created_at` is older than a new `STUCK_PROCESSING_THRESHOLD_MS`
  (5 minutes), the redelivery is now treated as a fresh attempt
  (`processRawEvent` reusing the same `rawEventId`) instead of
  `DUPLICATE_RAW`. The threshold is comfortably above any real
  concurrent-delivery race (which resolves in milliseconds) and
  comfortably below any operationally meaningful wait.
- Regression test (same file) proves the companion safety property: the
  identical arranged state, **not yet stale**, still correctly answers
  `DUPLICATE_RAW` with no lead created — the existing "concurrent identical
  deliveries produce exactly one lead" contract is unchanged (re-confirmed
  by re-running that exact pre-existing test, §15.5).

**Defect B — a crash during a replay attempt (the same double-fault
pattern, this time while reprocessing) leaves the canonical event stuck at
`PROCESSING` forever, with `replay()`'s own guard permanently blocking any
further attempt** (`current.status === 'PROCESSING' → EVENT_NOT_REPLAYABLE`,
unconditionally, regardless of age). Severity: **unrecoverable failure** —
once in this state, no mechanism in the system, automatic or
admin-triggered, could ever move it out.

- Reproduction: same file, "a stale canonical event stuck at PROCESSING
  can be reclaimed by a later admin replay; a fresh one is still correctly
  rejected" — a clean first failure, then a double-faulted replay attempt,
  confirmed to leave the row at `PROCESSING`.
- Fix (`IngestionService.replay()`): the guard now allows a `PROCESSING`
  row through once `updated_at` is older than the same
  `STUCK_PROCESSING_THRESHOLD_MS`, immediately re-processing it (not a
  separate "mark as dead" step — see §15.0's note on why `DEAD_LETTER`
  itself is not written: a transition straight to `DEAD_LETTER` and back to
  `PROCESSING` within the same commit would never be externally visible,
  so it would be pure churn). The same staleness check was also applied to
  the automatic redelivery-retry path in `run()`, so a provider redelivery
  can reclaim a stuck `PROCESSING` row exactly the same way an admin
  replay can.
- An admin-triggered reclaim is durably flagged — `audit_logs.metadata.reclaimedStuckProcessing: true` — regression-tested directly against the `audit_logs` table.
- Regression test proves the companion safety property: the identical
  stuck row, queried again **while still fresh**, is still correctly
  rejected with `EVENT_NOT_REPLAYABLE` — a genuinely in-flight attempt is
  never raced.

**Defect C — the raw-event retention purge deleted ANY expired row
regardless of its resolution status**, including one still `RECEIVED` or
`FAILED` — i.e., one whose ingestion decision (new lead vs. duplicate) was
never durably made. After the default 30-day retention window, an
unresolved accepted lead would be silently and permanently discarded with
no record it ever existed. Severity: **data loss**.

- Reproduction: same file, "an expired FAILED raw event survives the purge;
  an expired PROCESSED one does not."
- Fix (`apps/api/src/integrations/raw-event-retention.service.ts`): the
  purge query now additionally requires `status = 'PROCESSED'` — the one
  status that means the ingestion decision was already durably made, so
  the raw payload is no longer the only record of it. `RECEIVED` and
  `FAILED` rows are now never auto-purged, however long expired.
  Deliberately conservative: this also stops auto-purging a _permanent_
  business-rejection (`VALIDATION_FAILED`/`MAPPING_FAILED`, which also
  leaves `raw_events.status = 'FAILED'`) that will in fact never be
  retried — correct in the safe direction (never discard something whose
  resolution status does not unambiguously say it is safe to), but it
  means those rows now accumulate past the configured retention window
  until someone decides whether a finer, decision-aware purge policy is
  worth the added complexity. Flagged as a product decision in §15.4/§16,
  not resolved here.
- All five pre-existing purge tests (`integrations-hardening.int.spec.ts`)
  re-run clean: every one of them only ever created successfully-processed
  (`PROCESSED`) events, so the narrower filter changes nothing about their
  outcome.

### 15.3 What was NOT changed

- **Idempotency scope** (tenant-scoped, not source-scoped) — unchanged, per
  explicit instruction. Still documented as a pre-existing, open product
  decision (§13.1/§13.9), unaffected by this milestone.
- **No new infrastructure** — no new table, no new queue, no new scheduled
  sweep. The fix is a staleness check added to two existing code paths
  (`run()`'s duplicate-check branch, `replay()`'s guard) using the already
  existing `created_at`/`updated_at` timestamps. `DEAD_LETTER`/
  `NEEDS_REVIEW` remain defined-but-unused, exactly as before — not wired
  up, per the explicit instruction not to add a dead-letter state merely
  because it is a common pattern.
- **No retry-count cap was added.** An admin may still `replay()` an
  eligible event indefinitely; §15.1 item 11 concluded this is acceptable
  (it never falsely claims resolution) rather than a defect to fix.

### 15.4 Decisions requiring product-owner approval (new this milestone)

1. **Source/tenant validity mid-flight** (§15.1 item 13): confirmed, via a
   direct reproduction, that an event accepted before its source was
   revoked still completes successfully if later reclaimed/replayed — the
   revocation is never re-checked. Is a previously-accepted lead's
   processing allowed to complete after its source is revoked, or should a
   revoked source block even a previously-accepted event from ever
   producing a lead? Not decided; not changed.
2. **Retention vs. recoverability tradeoff** (Defect C's fix): permanently
   business-rejected raw events (`VALIDATION_FAILED`/`MAPPING_FAILED`) now
   accumulate past the configured retention window, since they share
   `raw_events.status = 'FAILED'` with genuinely-still-recoverable rows.
   Worth a finer purge policy (e.g., reading the canonical event's own
   terminal-vs-retryable classification) if raw-payload retention duration
   matters more than the added complexity — not required to close this
   milestone's defect.
3. **`STUCK_PROCESSING_THRESHOLD_MS` (5 minutes)**: a judgment call, not a
   measured SLA. Reasonable given real concurrent-delivery races resolve
   in milliseconds, but if this value is ever revisited it should be
   against real production latency data, not this session's reasoning
   alone.

### 17.2 Login rate-limit contention — root cause and the fix chosen

Root cause, confirmed directly against real `429` responses in a captured
API log (previous milestone): `LOGIN_RATE_LIMIT_MAX` defaults to 10 sign-ins
per 60 seconds **per email**, correct production behavior
(`packages/config/src/server-env.ts`). Running ~30 E2E tests with
Playwright's default parallel workers, repeatedly signing in as the same 2–3
demo accounts within the same minute, exceeds that window.

**Fix chosen**: set `LOGIN_RATE_LIMIT_MAX: '1000'` in the new job's own
`env:` block — nothing else. This is not a new mechanism and not a
production bypass:

- The exact same value is already used, for the exact same reason, by the
  backend's own integration-test harness
  (`apps/api/test/support/env.ts`: _"Many specs log in as the same fixture
  email repeatedly... would trip the real production login-throttle
  default. Generous here..."_) — a pre-existing, already-reviewed,
  already-safe convention, not a new one invented for this milestone.
- `LOGIN_RATE_LIMIT_MAX` is already a normal, validated, per-environment
  configuration value (`z.coerce.number().int().min(1).max(1000).default(10)`)
  — no schema, default, or application code was changed to make this
  possible; it was already designed to be set differently per environment.
- **It cannot reach production**: this value is set only inside this one
  GitHub Actions job's own `env:` block, read only by the ephemeral API
  process this job itself starts and destroys at job end. The deployed
  Railway environment's actual `LOGIN_RATE_LIMIT_MAX` (unset → the real
  default of 10) is configured entirely separately and is untouched by
  anything in this file.
- **Validated**: the identical curated spec list was run twice against a
  from-scratch local reproduction of this exact job (fresh database,
  `node dist/main.js` + `next start`, zero `.env` file — pure CI-style
  environment) with Playwright's default 4 parallel workers. Without the
  override: 4–5 of ~30 tests failed, every one at the sign-in redirect step,
  with the API log showing real `429 RATE_LIMITED` responses. With the
  override: those same specs passed — see §17.5 for the exact run.
- **Serial execution was considered and not needed**: once the real root
  cause (the throttle, not worker concurrency itself) was fixed, the
  default parallel worker count was sufficient; forcing `--workers=1` would
  have been a slower, less-targeted fix for a problem the rate-limit change
  already resolves completely.

### 17.4 Confirmed defects found while building and validating this job

Building a faithful local reproduction of the new job (fresh database, no
`.env` file, pure environment-variable configuration, default parallel
workers) surfaced two real, previously-undetected problems — not found by
guessing, found by actually running the curated spec list twice and
investigating every failure:

1. **Missing seed dependency** (test-infrastructure defect, in this
   milestone's own new CI job design): `platform-experience.spec.ts`'s
   branded-PDF assertion reads a finance invoice that only
   `seed:finance-demo` creates; that script was initially left out of the
   seed step (it is not one of the seven named critical-flow seeds on its
   own, but one of the chosen specs transitively needs it). Fixed by
   adding `seed:finance-demo` to the seed step (§17.1 item 3).
2. **A real, confirmed product defect** in `apps/web/components/hr/manager-picker.tsx`
   (the reporting-manager combobox used by `hr-core.spec.ts`'s "hire
   someone" test): `active` (the keyboard-highlighted option index) is
   reset to `0` on every keystroke, but the component's search results
   arrive later, asynchronously, on a debounced fetch with **no
   keystroke** to trigger that same reset. Under real latency (and
   reliably reproduced under CPU-contended parallel E2E workers, never
   under sequential execution — exactly the signature of a timing-dependent
   defect, not a flaky test), `active` can point at the wrong row — or, if
   the new result set is shorter, at no row at all — once the debounced
   results actually land. A keyboard-only user who types a name and
   presses Enter as soon as they see the right option appear can commit
   the **wrong** person as someone's reporting manager; a real business
   consequence (reporting-line errors, approval-chain errors), not a
   cosmetic issue, and also an ARIA 1.2 combobox correctness gap
   (`aria-activedescendant` should track the first match once results
   change).
   - **Fix** (smallest safe change): one `useEffect` resetting `active` to
     `0` whenever the search's resolved data changes, not only on
     keystroke.
   - **Regression test** added to `manager-picker.test.tsx`: confirmed
     failing against the pre-fix code (asserted, then reverted and
     re-asserted — not merely written and assumed) — simulates the exact
     race (highlight a row, then let a _different_, shorter result set
     arrive with no keystroke in between) and proves Enter now always
     commits the first row of the _current_ results, never a stale index.
   - Also fixed a related, much narrower test-robustness issue in
     `apps/web/e2e/platform-provisioning.spec.ts`'s "tenant list" test
     (already covered in §16.3 of this document before this milestone;
     unaffected by anything above).

No backend code and no business rule was changed to produce either fix.

### 18.3 The five-minute ingestion-recovery threshold — reviewed, not changed

Traced every source of legitimate, non-abandoned delay inside the window the threshold governs (between a canonical event committing `PROCESSING`/a raw event committing `RECEIVED`, and a terminal status):

- **The only real external I/O in that window** is `MetaGraphClient.retrieveLead()` (`apps/api/src/integrations/graph/meta-graph-client.ts`), called from `resolveDraft()` strictly between the two transactions. It enforces its own `AbortController`-based timeout: `DEFAULT_TIMEOUT_MS = 8_000` (8 seconds) — any Meta Graph API call that doesn't answer within 8s is aborted and thrown as a classified, retryable `HydrationError`, which `processRawEvent`'s own catch handler turns into a clean `FAILED` status (not a stuck `PROCESSING`/`RECEIVED`). **8 seconds is a 37.5× margin under the 300-second threshold** — no legitimate hydration call can come anywhere near triggering a false reclaim.
- **`processRawEventTx` itself** (the actual canonicalize/dedupe/lead-write transaction) performs no external I/O — only a handful of indexed reads/writes on small, per-tenant-scoped tables. No `statement_timeout` or `lock_timeout` is configured anywhere in `packages/db` or `apps/api` (confirmed by a repository-wide search finding zero matches) — in the most pathological theoretical case (an unrelated, abnormally long-held lock on one of these tables), a legitimate attempt COULD in principle exceed 5 minutes. This is a **pre-existing, independent fact about the database configuration, not introduced or affected by this threshold** — the same absence of a statement timeout would apply with or without the stale-reclaim logic.
- **Concurrent-request interaction, reviewed precisely**: the staleness check itself (`existingCanonical.updatedAt` / `rawEvents.createdAt`) is a plain, unlocked `SELECT` — two concurrent redeliveries (or a redelivery racing an admin replay) could both read "stale" and both attempt to reclaim simultaneously. This is **not a new risk**: the exact same unique-constraint-based serialization that already makes ordinary concurrent first-time deliveries safe (`canonical_lead_events`'s `(tenantId, idempotencyKey)` unique index — the first transaction to commit its upsert wins; the second's own dedupe lookup then correctly sees the first's already-committed lead) applies identically to two concurrent reclaim attempts. **Proven directly this milestone**, not merely reasoned about: a new test, "two concurrent redeliveries of the same stale orphaned row produce exactly one lead, never two" (`apps/api/test/ingestion-failure-recovery.int.spec.ts`), passes — confirmed via a real `Promise.all` double-fire against an arranged stale-orphaned row, asserting exactly one `DONE`, exactly one lead, exactly one canonical row.

**Conclusion: the 5-minute threshold is well-justified by the evidence available (a 37.5× margin over the only bounded legitimate delay) and does not need to change.** The one residual, theoretical risk (an unbounded DB lock-wait) is a pre-existing, independent property of the database configuration — worth a future decision (adding a `statement_timeout`) but out of this threshold's own scope to fix, and even in that pathological case the existing unique-constraint serialization prevents any actual duplicate lead or data corruption — at worst, a reclaim attempt would itself queue behind the same lock.

### 19.2 Database timeout resilience — investigated, not changed

**Confirmed from the repository** (`packages/db/src/client.ts`, the
single `pg.Pool` constructor site used by every connection in the
codebase — the RLS-scoped application pool, the migration/seed handle,
and the raw-event-purge context all share this one function): no
`statement_timeout`, `lock_timeout`, or `idle_in_transaction_session_timeout`
is ever passed to `pg.Pool`'s options, and a repository-wide search of
every migration file (`packages/db/drizzle/*.sql`) for `ALTER ROLE`/`ALTER
DATABASE`/any of those three settings returns zero matches. **This is a
genuine, confirmed-absent configuration, not an oversight in this
review.**

**Runtime/connection paths affected**: all of them, because there is only
one pool constructor. The application's request-serving queries, the
notification outbox dispatcher/delivery worker's own DB writes, the
raw-event retention purge job, and the migration/seed scripts all share
the same absence of a statement/lock timeout.

**Whether timeouts are already configured externally**: **NOT VERIFIED
from the repository** — Railway's actual managed Postgres service may set
its own server-level defaults (many managed providers do), but this is a
deployed, external configuration this session has no access to inspect.
This limitation is stated explicitly rather than guessed past: closing
it requires whoever holds the Railway dashboard to check the actual
Postgres instance's `SHOW statement_timeout;`/`SHOW lock_timeout;`.

**Failure modes a timeout could introduce, reasoned through concretely**:

- A `statement_timeout` applied to the SAME pool used for migrations
  (`createDb()` has no separate "migration-only" connection path — the
  distinction is only whether `appRole` is set, not the connection
  itself) could abort a legitimately long-running migration (e.g. a
  backfill on a large table) partway through, if ever added without first
  separating that connection path from the request-serving one.
- A `lock_timeout` would turn a transaction that is currently blocked
  waiting for a row/table lock into a visible `55P03 lock_not_available`
  error instead of waiting it out — generally the SAFER failure mode
  (fails fast and visibly rather than tying up a pool connection
  indefinitely), but nothing in the current codebase handles or retries
  that specific error code today; adding the timeout without also adding
  that handling would convert a rare, slow-but-eventually-successful
  operation into a user-facing failure.
- For context, not as a substitute: the notification worker's BullMQ
  config already uses an analogous, already-reviewed 5-minute figure
  (`stalledInterval: 300_000` in `notifications.worker.ts`) for detecting
  a stalled job — a different mechanism (lock renewal, not a DB
  statement timeout) but the same class of "how long before we treat
  this as stuck" decision, already made once in this codebase.

**Can a safe default be recommended without guessing at production
workload characteristics? No specific number — that would be guessing.**
What can be recommended is the methodology: measure the actual P99/P99.9
query duration from real production logs or APM over a representative
period (this session has no access to either), then set
`statement_timeout` on the request-serving connection only (never the
migration path) at a healthy multiple above that measured ceiling —
and only after also deciding how `lock_timeout` failures would be
surfaced/retried in the application. **No timeout value was chosen or
applied; this remains a recommendation for whoever owns production
database configuration, requiring real production timing data this
session does not have.**

### 21.2 Failure-handling procedure (applies to every check above)

1. Mark the check **FAIL** or **BLOCKED** (never silently skip it).
2. Capture: timestamp, release SHA, environment, sanitized logs
   (credentials/PII redacted), and exact reproduction steps.
3. Record impact and the affected tenant/module — using disposable
   staging identifiers only, never real customer data or secrets.
4. Assign an owner (role-based; `UNASSIGNED` if not yet named) and the
   next action.
5. Decide, with the responsible role, whether the failure blocks release.
6. After an approved fix, retest and retain **both** the original failing
   evidence and the retest evidence — never overwrite a failure record
   with its retest.

**Explicitly prohibited as a resolution to any failure**: suppressing the
failure, weakening a test, raising a rate limit globally (the one
sanctioned exception remains the CI-environment-only
`LOGIN_RATE_LIMIT_MAX` override already reviewed and confined to
`e2e-golden-paths`'s own job env per §17.2/§18.1 — never a production
value), or changing any security control to force a pass.
